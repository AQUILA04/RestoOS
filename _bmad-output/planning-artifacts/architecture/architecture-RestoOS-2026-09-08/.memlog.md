- (constraint) Multi-tenancy model required: Shared DB, Shared Schema with PostgreSQL RLS filtering on organization_id (UUID) and store_id (UUID)
- (constraint) API Response structure standard: wrapped in status, statusCode, message, service, data fields
- (constraint) Local offline creation uses UUID strings as primary keys; replaced by server ID upon sync to prevent conflicts
- (decision) AD-1 Paradigm: Spring Boot Modular Monolith with strict domain package isolation (tenant, catalog, order, kitchen, payment, audit)
- (decision) AD-2 Frontend: Nx Monorepo with dedicated apps (pos-app, kds-app, admin-portal) sharing core data-access and ui-components libraries; Angular standalone: false
- (decision) AD-3 Multi-tenancy: Shared DB + Shared Schema with PostgreSQL RLS enforced via app.current_org_id and app.current_store_id session settings set server-side per transaction
- (decision) AD-4 Real-time Messaging: Spring WebSocket + STOMP over SockJS with store-scoped topics (/topic/store/{storeId}/kitchen) backed by Redis Pub/Sub
- (decision) AD-5 Offline & Idempotency: Local creation uses client-side UUIDs and Idempotency-Key headers; server validates idempotency in Redis/DB and swaps UUID with server ID upon sync
- (decision) AD-6 API Response Envelope: Standardized Response.builder() wrapper with status, statusCode, message, service, data fields across all REST controllers
- (event) spine finalized
